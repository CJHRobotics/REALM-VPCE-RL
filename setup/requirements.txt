# Pin torch, and pin the CUDA BUILD, which is the part that bit us.
#
# Measured on GAIVI, 2026-11-24, same node, same card, same driver
# (530.30.02, a CUDA 12.1 driver), same arch list in both wheels:
#
#   realm-vpce     torch 2.5.1+cu121   ->  allocates on a GTX 1080 Ti
#   realm-vpce-rl  torch 2.14.1+cu126  ->  cudaErrorDevicesUnavailable
#
# Both wheels list sm_50, sm_60, sm_70, sm_75, sm_80, sm_86, sm_90 and
# neither lists sm_61, so the missing arch -- which looked like the answer
# for most of a day -- is not it. The cu126 runtime cannot work with a 12.1
# driver on this hardware; the cu121 one can. Minor-version compatibility is
# supposed to make that fine and here it does not, which is exactly why this
# is pinned to a measurement rather than to a rule.
#
# Both repos said plain `torch`. The only reason one environment worked is
# that it was built on an earlier day and got an earlier wheel -- a
# difference nobody chose and nobody could see. So:
#
#   pip install --force-reinstall torch==2.5.1 \
#       --index-url https://download.pytorch.org/whl/cu121
#
# The index URL is not optional ON GAIVI: plain `pip install torch==2.5.1`
# from PyPI gives whichever CUDA build is default there, which is how this
# started. If the cluster's driver is ever upgraded, re-measure before
# moving: the test is slurm/gpu_check.sh, and it takes a minute.
#
# On macOS there is no cu121 wheel to get, and nothing to get it for. Plain
# `pip install torch==2.5.1` is correct there. What matters off the cluster
# is that the VERSION matches: a model.zip written by one torch and read by
# an older one is the next version-skew bug waiting to happen, and the
# laptop venv was on 2.2.2 while the cluster moved to 2.5.1.
torch==2.5.1          # +cu121, see above
gymnasium==1.2.3      # resolved alongside SB3 2.8.0, same provenance
# Pinned to what pip resolved against torch 2.5.1, read back out of a
# model.zip that trained successfully on GAIVI -- so this is the version a
# result was actually produced with, not a guess. 2.9.2 requires torch>=2.8
# and is out of reach while torch is pinned.
#
# It matters off the cluster too: a model.zip written by 2.8.0 and read by
# 2.4.1 cannot unpickle the training schedules, because FloatSchedule did
# not exist yet. Inference survives that; anything that resumes training
# does not.
